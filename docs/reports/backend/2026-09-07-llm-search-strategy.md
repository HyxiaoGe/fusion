# 搜索策略由模型控制：实现与验收

## 原始证据

真实会话 `97e8182e-74d3-4b0b-8f3f-925eb617e20b`，Run `7e3369c3f104498096b33b75d25b650b`，问题“英伟达投资Perplexity意味着什么？”。两次搜索实际分别请求3/5条，返回2/5条，读一篇转载后结束；正文出现无法解析的 `[U1]`。对比用户既有页面：豆包4关键词18资料、DeepSeek11网页、千问17搜索来源、ChatGPT19来源（各平台展示口径不同），原始报道覆盖更广。

根因包括：工具未暴露count；服务端意图预算覆写3/5条；提示词限制普通问题最多两次、同语言且强制年份；未传recency时客户端默认最近一周；url_read未接收运行级编号并硬编码U1。

## 四项实现

1. 多角度、多批次：提示词要求按事件原始报道、业务关系、独立分析等证据需求选择查询角度，同轮多个web_search复用现有并行执行器，后续按缺口继续。移除普通最多两次与语言/年份限制，不强制每个简单问题搜多次。
2. 结果规模与筛选：新增模型count参数，默认10，范围1–20，保留URL去重和同域多样性处理；全局来源注册表复用跨批编号。上下文摘要仍受治理配置上限控制，超出的来源只展示编号、标题和URL，允许模型选择继续读取，不作为已读证据。
3. 证据与引用：提示词要求核对原始来源、日期、独立性及矛盾，缺口存在则继续搜/读。url_read接收运行级编号，搜索后读同URL复用编号，新URL递增；失败不伪造编号。候选元数据不能通过失败恢复证据门禁，成功读页后可登记。历史U1无法唯一映射，未猜测重写。
4. LLM控制：模型决定关键词、批次、count、语言、时效和是否继续；服务端保留总搜索40次、读页100次和运行总预算，按完整请求签名去重。旧DB里的意图/追问/repair小数量、旧计划次数不再参与执行，无需数据库迁移。未指定recency时传空时间过滤，保留历史原始报道。

## 验证

- 搜索schema与客户端先红后绿，验证count暴露和无默认一周窗口。
- 实际runner→tool_round→executor→handler的隔离集成用事件屏障证明同轮2/3/4搜索并行，独立count10–13及后续16/18到达provider；普通问题可进行第三批检索和后续读页，tool_call_id与引用不混淆。
- 旧DB配置、同关键词不同domain/recency/count、相似词互补搜索、完全相同请求去重、全局预算耗尽均有回归。
- 同页复用编号、新页编号与持久化source_refs一致；metadata不能当作读过正文的证据。独立审查发现此P1后已修复并验证，无剩余可达P0/P1。
- 前端现有引用模型和来源面板4文件64项Vitest通过。改动Python Ruff与git diff检查通过。
- 最终完整后端unittest：3049项，50.576秒，OK（skipped=2）。旧数量断言按真实输入更新，耗尽不执行handler及事件顺序断言保持。
