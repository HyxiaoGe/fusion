## 真实页面发现

复用用户现有 Chrome 标签，在 dev 页面会话 `41e2c744-44c5-4f75-b864-de5e8366370f` 发起 Python 官方文档查证，进行到搜索与读取后点击停止。Run `167f82d5c0554ed88896d8dc45479416` 最终为 `interrupted`，停止反馈在当前页面出现，刷新后仍显示已中断；但轨迹为 `degraded`，原因不是 `recorder_timeout`，而是 `finalize_mismatch`。

数据库只读核对：轨迹有 54 条事件，序号 `0–52` 和 `54`，缺 `53`；`llm_round_cancelled` 为 `52`，`run_interrupted` 为 `54`。停止冻结 Redis 写入后，终局计划快照这个普通事件因 `StreamOwnershipLostError` 被拒绝，但 `AgentEventEmitter` 已预占序号。取消尾事件由轨迹旁路保存，形成缺口；完整性校验正确地标为降级。页面提示并非缓存问题，刷新后仍可复现。

## 本地修复与验证

- 对 Redis 明确拒绝的**普通**事件回退预占序号；对可能已经由轨迹旁路保存的取消终态继续保留序号。其他不确定写入失败继续使用原有保守语义。
- 新回归用例在修复前复现 `[0, 1]` 缺口，修复后为 `[0, 0]` 重用拒绝事件的序号；数据库集成用例覆盖“计划快照被拒绝→取消尾事件入账→轨迹完整”。
- 受影响的 4 份测试文件共 `157 passed`、`28 subtests passed`；Ruff lint、格式和 `git diff --check` 通过。本轮未做修复版 dev 部署与真实页面复验，不能将本地通过记为发布验收。

## 后续判定

当前已确认一个停止路径轨迹完整性缺陷，并有本地修复。独立 MCP 别名误分类值得后续单独定位；纯规则兜底的低覆盖率也需要先决定目标覆盖范围，再据此改动。默认动态工具发现仍应维持现状，直到显式发现路径完成真实模型端到端验收。
