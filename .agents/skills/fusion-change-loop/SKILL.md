# Fusion 开发

先以 `git rev-parse --show-toplevel` 和 remote 确认当前 `HyxiaoGe/fusion` worktree，遵循根及受影响应用的 AGENTS.md。本 skill 的权威版本随仓库维护，全局安装副本不覆盖当前仓库版本。

用户指定的工作树优先。当前目录不是 Git 仓库时，从本 skill 文件的真实路径向上查找所属仓库并核对 remote；不要默认选择父目录下的旧 API/UI 仓库。

## 决策要点

- 从用户请求明确现象、预期行为、授权终点与验收环境；已有上下文足够就直接做。只调查时只采集证据，不转成实现。
- 小修复直接沿实际入口定位、实施、验证。跨组件、协议或高不确定性改动先写短计划；只有需要长期追踪或用户要求时才落文档，不为常规步骤另设设计审批。
- 排障先形成可证伪的假设，用调用链、复现、日志或针对性测试验证。证据否定假设时重新定位，避免持续叠补丁。
- 用最小完整改动满足当前用户行为，检查共享状态、失败路径和必要的刷新/历史兼容，不顺带重构。优先沿现有入口修正根因，不为尚未出现的第二种实现、后端或策略预建插件系统、配置层或通用框架。
- 新增抽象、依赖或跨模块重构前，说明它解决的已确认问题，以及沿现有结构直接修改为何不够；复杂任务的短计划里交代即可，不另设审批或长设计文档。必要的公共修复可以扩大到相关调用点，但应减少实际重复或状态复杂度，使调用链和排障仍可追踪。
- 流式、认证、持久化或跨应用契约变更，检查生产者到最终消费者并安排独立审查。可独立且确有收益的调查/实现可以委派；主代理保留集成、实际差异核对和交付责任。

## 证据与终点

- bug 修复优先让回归用例暴露原故障，再验证修复；视觉或难以自动复现的问题先定义可观察的前后差异。不要把“先写测试”变成所有文件改动的仪式。
- 运行受影响测试及应用要求的检查。全量套件依变更范围和 CI 门禁决定；通过后仅因新改动、失败或未解疑点重跑/扩展。
- 需要运行效果时使用仓库 `fusion-acceptance`。本地启动、真实 dev 写入或收费调用需已有对应授权；缺少某个验收条件时完成其他工作并明确缺口。
- 只到本地的任务：核对 diff、相关验证和工作区，报告结果。已授权 push、PR 或发布：继续仓库 `fusion-release-gate`，不让用户重复授权已有动作。
- 交付说明用户问题的变化、关键验证与尚未确认的部分。检查通过不能替代真实效果，当前无法验证的行为不得标成已通过。
